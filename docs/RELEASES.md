# שחרור גרסאות — TradeOS

המסמך הזה קובע מתי מותר לקדם קוד, ואיך רושמים את השחרור. `docs/VERSIONING.md` נשאר ההסבר להבדל בין `APP_VERSION` (גרסת המוצר, ידנית) לבין `CACHE_NAME` (קאש של ה-Service Worker, עולה לבד בכל דחיפה ל-`main`). אם יש סתירה לגבי אישור — המסמך הזה גובר.

הגרסה הבאה יוצאת מהגרסה שכבר קיימת: `APP_VERSION` ב-`src/utils/constants.js` הוא `2.2.1`. `package.json` עומד על `0.0.0` וזה לא מספר המוצר. אין תגיות `git`. אין `1.0.0` חדש.

## זרימה

```
PR של פיצ'ר  →  dev  →  בדיקה ב-staging  →  PR ‏dev→main (merge commit)  →  תג vX.Y.Z
```

1. ענף פיצ'ר נפתח מ-`dev`. ה-PR נכנס ל-`dev` רק אחרי שאברהם כותב במפורש **מזג**.
2. אחרי המיזוג ל-`dev` בודקים ב-staging. ערוץ `dev` וה-Worker ‏`trade-os-staging` חולקים את Firestore של הפרודקשן. לא שומרים נתונים אמיתיים בבדיקה, ולא לוחצים שמירה על תוכנית או על מפתח בורסה.
3. שחרור הוא PR מ-`dev` אל `main` עם **merge commit**, לא squash. הוא רץ רק אחרי שאברהם כותב במפורש **מזגי לפרוד**. המילה «תקין» אינה אישור, לא ל-`dev` ולא לפרודקשן.
4. אסור `force push`. לא ל-`dev`, לא ל-`main`, ולא לענף של השחרור.

דחיפה ל-`main` מפעילה את הפרודקשן: Hosting, ה-Worker ‏`trade-os`, וגם את `tradeos-alerts`. `scripts/bump-version.mjs` מעלה רק את `CACHE_NAME`. הוא לא נוגע ב-`APP_VERSION`.

## מספור

הפורמט הוא `MAJOR.MINOR.PATCH`, על בסיס `2.2.1`.

| | מתי | דוגמה מהמצב הנוכחי |
|--|--|--|
| **PATCH** | תיקון באג בלבד | `2.2.1` → `2.2.2` |
| **MINOR** | פיצ'ר חדש, או שינוי תואם לאחור | `2.2.1` → `2.3.0` |
| **MAJOR** | שבירה: חוזה API או MCP, מודל נתונים שדורש מיגרציה, או הסרת פיצ'ר | `2.2.1` → `3.0.0` |

את המספר מעלים רק בתוך שחרור שאושר. PR רגיל ל-`dev` לא משנה את `APP_VERSION`, לא את `package.json`, ולא יוצר תג.

## מתי משחררים

אחרי שמנה מצטברת ב-`dev` ונבדקה ב-staging. באג דחוף יכול לצאת לבד כ-PATCH.

מציעים שחרור כשממתינים 3 PR משמעותיים או יותר, או פיצ'ר שהמשתמש רואה. לא משחררים סמוך לשבת, לחג, או מאוחר בלילה לפי שעון ישראל, אלא אם התקלה דחופה ואברהם אישר את הדחיפות בנפרד.

## לפני השחרור

- `npm test` עובר.
- staging נבדק על מה שנכנס מאז השחרור הקודם.
- אין סודות ב-diff.
- שינוי כללי Firestore, מיגרציה, או כתיבה לנתוני פרודקשן מסומנים בנפרד ודורשים אישור נפרד מאברהם. אישור השחרור לא מכסה אותם.
- ניהול עסק: לפרסם קודם את כללי `users/{uid}/businessEntries` לפרודקשן, ורק אחרי שהפרסום הצליח להפוך את `BUSINESS_LEDGER_FIRESTORE_ENABLED` ב-`src/services/businessLedgerStore.js` ל-`true`. כל עוד הדגל `false` העמוד נשאר על דמו ולא קורא ולא כותב ל-Firestore. אסור להדליק את הדגל לפני פרסום הכללים.
- מחברת: לפרסם קודם את כללי `users/{uid}/notebookEntries` לפרודקשן (אישור נפרד מאברהם), ורק אחרי שהפרסום הצליח להפוך את `NOTEBOOK_FIRESTORE_ENABLED` ב-`src/services/notebookStore.js` ל-`true`. כל עוד הדגל `false` העמוד נשאר על דמו ולא קורא ולא כותב ל-Firestore. אסור להדליק את הדגל לפני פרסום הכללים.
- סודות ה-Worker לא השתנו, או שהשינוי רשום במפורש.
- תוכנית חזרה: `git revert` של ה-merge commit על `main` (בלי force push), ואז Rollback ל-release הקודם ב-Firebase Hosting. ה-Worker חוזר לפריסה של הקומיט הקודם על `main`. `CACHE_NAME` שכבר עלה לא מורידים ידנית.

## אחרי השחרור

1. תג `vX.Y.Z` על ה-merge commit ב-`main`. לא יוצרים תג לפני שהמיזוג אושר.
2. GitHub Release עם הערות בעברית ורשימת ה-PR.
3. רשומה ב-`CHANGELOG.md`. מה שהיה תחת `Unreleased` עובר לגרסה, ו-`Unreleased` מתרוקן.

## תבנית הערות שחרור

```markdown
# vX.Y.Z

תאריך: YYYY-MM-DD (שעון ישראל)
טווח: PATCH | MINOR | MAJOR
מאישור: מזגי לפרוד

## מה השתנה
- #NNN כותרת קצרה בעברית

## בדיקות
- npm test עבר
- staging נבדק

## לא כלול באישור
- כללי Firestore / מיגרציה / נתוני פרודקשן: אין | פורט, באישור נפרד
- סודות Worker: ללא שינוי | פורט

## חזרה לאחור
revert של merge commit <sha> על main, ו-rollback של Hosting ל-release הקודם.
```
