## מספר מוצע

המנה מוסיפה מסכים ויכולות (מחברת, הכנסות והוצאות, שדות מותאמים, שיתוף יומן, כללי סיכון, סיור) בלי שבירת חוזה API ובלי מיגרציה. לפי הטבלה ב-`docs/RELEASES.md` זה MINOR, לא PATCH ולא MAJOR.

את `APP_VERSION` מעלים רק בתוך השחרור שאברהם אישר במילים **מזגי לפרוד**. לא נוגעים ב-`package.json`. לא נוגעים ב-`CACHE_NAME`: הוא עולה לבד בדחיפה ל-`main`.

### 2. פרסום כללי Firestore — אישור נפרד

דחיפה ל-`main` לא מפרסמת כללים. הפרסום ידני, והוא מעלה את כל קובץ הכללים:

```bash
firebase deploy --only firestore:rules --project tradeos-91a58
```

- [ ] אברהם כותב אישור נפרד לפרסום הכללים האלה.

Firestore משותף ל-staging ולפרודקשן. הכללים חלים על שניהם ברגע שהפרסום מצליח.

## חזרה לאחור

אם בדיקות העשן נכשלות:

1. `git revert` של ה-merge commit על `main`. בלי `force push`.
2. Rollback של Hosting ל-release הקודם (Firebase Hosting → Release history).
3. ה-Worker ‏`trade-os` וה-Worker ‏`tradeos-alerts` חוזרים לפריסה של הקומיט הקודם על `main`.
4. `CACHE_NAME` שכבר עלה לא מורידים ידנית.

החזרת הקוד מחזירה את שני הדגלים ל-`false` אם הם נכנסו באותו מיזוג. העמודים חוזרים לדמו ולא כותבים.

פרסום הכללים לא מתבטל עם ה-revert. הכללים שכבר פורסמו נשארים: קריאה וכתיבה של הבעלים בלבד. לא מוחקים אותם כחלק מהחזרה. דגל `false` מספיק כדי שהלקוח יפסיק לגעת באוספים.

אם רק הדגלים בעייתיים והשאר תקין, מחזירים אותם ל-`false` בקומיט על `main` בלי לבטל את שאר המנה, ורק אחרי שאברהם מאשר את החזרה הזו.
